03 · Reference pattern

The Vault Contract Pattern — one Decision Card field, four reference surfaces

Explain this page:

The AI Procurement Decision Card includes data_vault_targets[] to declare candidate field protections and reveal roles. The four open-source surfaces below illustrate where an approved contract could be applied. Their presence in source does not establish a buyer-signed card, a shared production route, or complete audit delivery.

A Decision Card can record which sensitive fields a buyer approves, how they should be protected, and which roles may see them. These four projects explore how to carry those rules into different workflows. Each deployment still needs a real buyer approval, trusted identity and policy facts, an integrated data path, and tests of the actual boundary.

A company could write down which customer fields a vendor may use and how to protect them. These projects show possible places to check that record, such as document ingest and a human review screen. They are reference software; a working, buyer-approved deployment must still be connected and tested.

One proposed contract, four integration points. The schema uses vault-oriented field names, while adapters may target different vaults. No single signed buyer contract has been verified flowing through all four projects, and their event paths have not been proven complete against an independently held audit checkpoint.

Suite × Implementations — the repos that implement it

The Suite is a set of specs; these are related source repositories grouped by likely user. Their cross-repo hooks are integration patterns. A source repo or passing local test does not establish a deployed, authenticated, buyer-approved request path.

Procurement reviewer 2 repos

FastAPI service that drafts AI Procurement Decision Cards from a buyer rubric and a set of vendor Suite documents (AEO + agent-card + tool-card + ai-evidence + …). The first cross-ecosystem bridge in the portfolio — Suite × Decision Intelligence.
